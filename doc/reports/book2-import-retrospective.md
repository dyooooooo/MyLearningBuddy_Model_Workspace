## 第一部分：改动点归纳（人在中栏盯页时改了什么）

### 1. 执行摘要

第二册的页级修正**几乎全部发生在全书导入会话内**：用户中栏聚焦页/块 → Agent 改中间表示（IR）写盘 → 界面询问是否记入方案待审议。全库从未创建 `page_assist` 分诊会话。

| 指标 | 数量 | 含义 |
|------|------|------|
| 用户聚焦改页 | **124 次** / 覆盖 **84** 个不同页 | 人驱动的「点哪改哪」 |
| 写盘账本 `layout_change_log` | **125** 条 | 工具成功改 IR 的自动记录 |
| 确认账本 `effective_changes` | **157** 条 | 记入方案「待审议」或 Agent 主动记账 |
| 遗留问题 `open_issues` | **106**（fixed 92 / 用户跳过 14） | 版式 69 + 公式 37 |
| 写盘手段 | `patch_block` **103** + `replace_page_blocks` **22** | **无** 35B `reprocess` |
| 写盘触及页 | **46** 页（账本有 page 字段的） | 与聚焦 84 页不完全重合 |

**一句话提炼：**
高频痛点集中在 **公式结构、插图配对/裁切、习题编号与选项排版、页眉页脚、表格标题与宽度、分栏/侧栏**；手段以 **单块 patch** 为主，整页 replace 为辅；方案侧多数标为 **非越权（edition）**，适合沉淀进规则/待审议，而不是每次手改。

### 2. 改动是怎么管理的（本报告的坐标系）

```text
用户聚焦页/块
    → Agent 改 IR / 重渲染（写盘）
    → layout_change_log 自动追加
    → 前端「记入待审议？」→ effective_changes + 方案 correction 队列
    →（会话级）finalize → fork 新方案草稿
```

| 层 | 存什么 | 本样本规模 |
|----|--------|------------|
| 写盘 | 当前 job 的页 HTML/IR 已变 | 125 条 log |
| 确认 | 「值得进方案」的改进点 | 157 条 effective |
| 沉淀 | 新方案草稿 id | `hujiao_math_hs_v1_ai_20260725` |

## 第二部分：来源归因（这些错到底是谁造成的）

**核心问题**：事后改的那些错，到底是 **MinerU（识别/导入基线）一开始就错**，还是 **Cursor Agent 自动改/质检改坏的**？

### 7. 归因结论

不能简单二分。本样本实际是 **三类来源**：

| 来源 | 是什么 | 本样本中的分量 | 典型例子 |
|------|--------|----------------|----------|
| **A. 导入基线错** | MinerU 结构 + 几何/规则写出的「最终页」本身就不对 | **主体** | 缺表题、页眉不全、公式结构坏、缺图、落栏错；门闸曾标出 **106** 个问题页 |
| **B. 流水线合并写坏** | 分段 `extend_import` 合并全书 IR 时按 **block id** 排序，打乱阅读序 | **系统性、很重** | 目录/章名跑到页尾；约 **150/178** 页曾 storage 序 ≠ `order` |
| **C. Cursor 改页引入/放大** | 用户点「按建议改」或事后聚焦时，Agent `patch`/`replace` 改错或改不彻底 | **局部存在** | 图配对「又反了」、同页反复改表宽仍不对 |

一句话：

> **大部分「内容/公式/图/栏」问题：一开始（导入基线）就有。**
> **「整页首尾颠倒」大面积事故：中间分段 extend 流水线写坏的**，不是 MinerU 识别反了，也不是 Cursor 手改目录页改反的。
> **Cursor 的责任**：在「按建议改」和聚焦阶段修基线问题；有成功也有改错/改不干净；并曾误判/热改渲染代码（后被 fs_guard 回滚）。

### 8. 时间线（为什么能分清「一开始」和「后来」）

本会话跑的是 **当时的分段导入**（每批约 20 页 + 门闸）：

```text
每批：
  MinerU 导入本批就绪
    → Cursor 质检：按「当时最终 HTML」列出问题页（门闸）
    → 用户：「按建议改」或「不修，下一批」
    →（若按建议改）Cursor patch/replace 写盘
    → extend 下一批（此处会触发全书 IR 合并排序）
…
全书导入 + 各批质检结束后
    → 用户又发现阅读序大乱、表公式等
    → 再进入大量「聚焦目标」事后改页
```

| seq | 事件 | 归因意义 |
|-----|------|----------|
| 20 | 第 1–20 页 MinerU 就绪，开始质检 | 此后立刻列出的问题 ≈ **基线错** |
| 82 | 列出问题页 1,3,8–16,18–20 | **在第一次「按建议改」之前** → 非 Cursor 补丁造成 |
| 84 | 用户「按建议改」 | Cursor 开始改这些页 |
| 96+ | `reprocess_done` / 写盘 | Cursor 写盘阶段 |
| 375 | 「不修，下一批」 | 第 1 批剩余问题 **带着基线错进入后面** |
| 378+ | 各批 extend + 多次「按建议改」 | 合并排序 bug **从第 2 批起反复发作** |
| 988–1022 | 用户投诉目录/章名跑到页尾；追问「谁改的」 | Agent 结论：`extend` 按 id 排序 |
| 1037+ | 大量「聚焦目标」 | 事后修：基线残留 + extend 乱序余波 + Cursor 局部改错混在一起 |

首次聚焦在 seq **1037**。此前已有 **62** 次页写盘事件；此后聚焦阶段还有 **77** 次——说明「自动质检改」和「人事后盯页改」两段都重。

### 9. 来源 A：导入基线（MinerU + 几何/规则）

**证据：**

1. **门闸问题页出现在「按建议改」之前**——第 1 批 seq 82 列出 14 页问题，seq 84 才「按建议改」；后续各批同样是「先列问题 → 再按建议改」。
2. 各批问题页并集约 **106** 页，与后来 `open_issues` 规模同量级。
3. 用户聚焦原话大量直接说 **「识别」**：封面乱、缺表 6-1 标题、页眉「6 三角」没进结果、左栏识别差、公式识别错误、截图错误等（启发式约 **31** 条偏识别表述）。

**注意**：门闸看的是 Worker 产出的**「最终 HTML」** = MinerU 结构 + 几何/规则，**不纯是**裸 OCR。归因上归为「导入基线」比单说「MinerU OCR」更准确。

### 10. 来源 B：分段 extend 合并——中间写坏

**用户现象**：第 6 页目录跑到页尾；第 7 页「第 9 章」跑到页尾。用户明确说「这也是最近才改出来的」，并追问是谁改的。

**Agent 自查结论（会话内，有代码位置）**：不是当晚改表格 `$`→math 动的 6/7 页，也不是各批 `replace_page_blocks` 点名改了 6/7，而是 `extend_import` 合并时：

```python
# learning-buddy-api/app/services/corpus_import.py 约 L533（2026-07-30 时的状态）
merged.sort(key=lambda b: (int(b.page_no), str(getattr(b, "id", "") or "")))
```

按 **(页码, block id 字符串)** 排序，**打乱**正确的 `order` / 阅读序。第 1 批单独导入时基线目录仍可用；**从第 2 批 extend（约 15:18）起**全书 IR 数组序被打乱。放大器：渲染若按**数组存储序**而非 `order`，HTML 必跟错。约 **150/178** 页曾不一致。

> **2026-08-03 现状更新**：`extend_import` 整条链路（Copilot 工具、buddy-api `.../extend`、
> c2-gateway 代理、worker `extend_mode` 分支）**已全部删除**，`corpus_import.py` 中
> 已无任何 `sort` 调用，上述根因代码不复存在。此故障模式不会在现行全书一次导入中复现。

| 问法 | 答案 |
|------|------|
| 是 MinerU 识别把目录识别反了吗？ | **否**（baseline 里 order 仍对） |
| 是 Cursor 手改第 6/7 页改反了吗？ | **否**（未点名改这两页） |
| 是「AI 导入过程」弄坏的吗？ | **是**——编排器驱动的 **extend 合并逻辑**（流水线 bug） |

### 11. 来源 C：Cursor Agent 改页——修基线时引入或放大

**明确发生过的 Cursor 阶段**：用户 **9 次「按建议改」**；聚焦前已有大量 `patch_block` / `replace_page_blocks` 写盘；聚焦后用户继续让 Agent 改（124 次聚焦）。

**更像「Agent 改错 / 改不干净」的信号**：用户聚焦原话中偏「越改越怪 / 又反了 / 你现在没对齐」的约 **9** 条——图示位置颠倒、「你现在没有对齐」、「又反了」（图 9-2-5 / 9-2-6）、上下颠倒（在 extend 乱序语境下也可能是 B 的余波）。

同页反复改表宽仍失败（第 15 页用户抱怨改两次仍不对）→ 更像 **CSS/预览 critical 样式锁死**（后来走了 `fs.request_edit`），责任在渲染栈 + Agent 未先查根因。

**Cursor 越权改代码**：阅读序排查时 Agent 曾直接改 `document_ir.py` 等并被 **fs_guard 回滚**，会话失败。说明 Agent 阶段有「乱改核心」风险。

**不要夸大**：多数聚焦批注仍是中性描述（「应放入右栏」「例题不应作 title」「加 caption」），**无法从措辞断定**是基线错还是 Agent 改坏——结合门闸「先列问题再改」，**先验仍是基线错居多**。

### 12. 汇总：改变点类别 × 更可能来源

| 改变点类别 | 更可能来源 | 依据 |
|------------|------------|------|
| 缺表题 / 页眉不全 / 公式结构 / 缺图裁切 / 落栏 / 例题当标题 | **A 基线** | 门闸先列出；用户称「识别」 |
| 目录/章名跑到页尾、大面积上下颠倒 | **B extend 排序 bug** | 会话自查 + 当时源码；MinerU order 仍对 |
| 图「又反了」、对齐不对、同页反复改不好 | **C Agent 改页** 或 **A+C** | 聚焦措辞；需对照改前 HTML 才能百分百 |
| 表宽滚动条、预览 CSS | **渲染/CSS（基线展示层）** + Agent 未一次查清 | 后靠 theme / critical CSS 修复 |
| 待审议里大量 figure/math | 多为修 **A** 的沉淀，不证明是 C 造的错 | effective_changes 是「修好后记账」 |

## 第三部分：优化动作

### 13. 应优先做成规则 / 方案数据的（高 ROI）

1. **例题不作 heading**（S1）
2. **（1）（2）编号与 list 冲突**（E1）+ **选择题两列/小问网格**（E2/E3）
3. **页眉 running 补全**（H1）
4. **表 caption 契约 + 宽表 CSS**（T1/T2/T3）
5. **CJK 不进 bare latex**（M1）
6. **块默认栏位（layout_zone）**（L1）对系统性质疑页

→ 做一次规则，少几十次聚焦。规则落在 `<edition>/layout_rules.yaml`，不是 `policy.entries`。

**适合批处理 / 模板的**：子图 caption 模式（F4）；缺图检测清单（F1）在 escalate 或导入后自动列出；长公式 nowrap/分行策略（M4）。

**难规则、宜保持「聚焦改块」的**：图配对颠倒（F2）、裁切对错（F3）——依赖原书对照，个案强；个别证明步骤补全。

### 14. 流程 / 产品层

| 问题 | 改变点侧表现 | 优化方向 |
|------|--------------|----------|
| 同页改太多次 | 单页 7–9 条 log | 同症检测 → 改规则再 rebuild 一批页 |
| kind 空/过泛 | 21 条空 kind、23 条 content_correct | promote 卡强制选细类；与 §4 的 ID 对齐 |
| 账本与聚焦页不一致 | 84 vs 46 | 每次写盘必带 page；失败也记 issues |
| 待审议偏插图 | 人更认图类价值 | 导入后自动跑「缺图/图序」检查 |
| 分不清来源 | A/B/C 混在一起统计 | 聚焦改页打标：`baseline` / `extend_order` / `agent_regression` |

### 15. 与现行 Pipeline 的对齐

| Pipeline 阶段 | 与本报告的关系 |
